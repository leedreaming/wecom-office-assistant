# 开发记录与踩坑（Development Log）

本文记录项目从 0 到 1 的真实过程与关键问题，供二次开发/排障参考。

## 2026-11-23 · v0.1.0 首次跑通

**目标**：手机企业微信 → 机器人 → 电脑执行 → 结果/文件回传手机。

- 采用企业微信官方「智能机器人 + WebSocket 长连接」方案，确认**不需要公网回调地址**；
- 使用官方 `wecom-aibot-python-sdk` 接入，文本/语音消息解析、流式回复；
- 接入本机 DeepSeek Harness 桌面版：自动发现监听端口、读取本地凭证、创建/复用会话、
  下发任务并轮询结果；
- 首次真实交付：手机下发任务 → 电脑执行 → 文档生成 → 文件卡片回传手机。

**结论**：链路可行，「聊天软件当遥控器」体验成立。

## 2026-11-24 · v0.2.0 双执行端与长任务

### 新增

- `engine = auto | dsh | api`：DSH 在线真执行，离线自动用 DeepSeek API 纯聊天兜底；
- `/stop`（及「停止当前任务」等自然语言）——长任务占锁也能立即中断；
- `/status`、`/help`、`/new`，以及「告诉我一下版本号」等自然语言状态查询；
- 长任务结果主动推送，规避企业微信流式消息 **10 分钟上限（errcode 846608）**；
- 任务完成通知（≥1 分钟的任务额外推送摘要+耗时）；
- 文件回传（分片上传 + md5 + 文件卡片）；
- DSH 审批自动化（`dsh.auto_approve`），让无人值守任务不卡「等待批准」；
- 离线自测 `selftest_engine.py`（假 API 服务器 + 引擎路由 + 安全回归，20 项）。

### 当天踩的坑（真实）

| # | 现象 | 根因 | 修复 |
|---|---|---|---|
| 1 | 写了 API Key 但机器人仍说「未配置 API Key」 | `_ask_with_fallback` 在 `ask()` 之前判断 `configured`，而热加载发生在 `ask()` 内部 | 先热加载再判断配置 |
| 2 | 「任务完成通知」永远不发 | `on_message` 的 `finally` 先 `task_meta.pop()`，后面判断时已为空 | 把清理移到通知之后 |
| 3 | 任务报「等待超时 900s」，实际 DSH 在等审批 | `session/wait` 的 `input-required` 被误判为超时 | 识别 `input-required` → 自动 cancel + 中文提示 |
| 4 | DSH 明明在线却降级 API「瞎答」 | 探活瞬时超时被误判离线 | 失败重试一次 + 在线缓存 + 失败原因写状态 |
| 5 | `session/wait` 偶发返回空 | 误当超时处理 | 空值 → 继续等待 |
| 6 | 直接 `session/create` 已存在会话导致 DSH 断连 | 重复创建不合法 | 先 `session/state` 查存在性 |
| 7 | 长任务最终结果发不到手机 | 流式消息 10 分钟过期 | 主动推送兜底 |

**设计沉淀**：执行端错误分级——只有「不可用」才允许降级 API；
「已受理但失败/超时」绝不静默重试，避免同一条指令在电脑上执行两遍。

## 2026-11-25 · v0.3.0 稳定化与开机自启

### 新增

- Windows 计划任务 + 纯 ASCII VBS 隐藏启动，实现登录自动上线（冷启动约 28 秒）；
- 单实例保护：PID 文件 + WMI 校验命令行含 `wecom_bridge`；
- `setup.ps1` 支持离线 wheels / 在线镜像自动回退；
- 运行环境与项目目录解耦（`WECOM_VENV`）。

### 当天踩的坑（真实）

| # | 现象 | 根因 | 修复 |
|---|---|---|---|
| 8 | 重装系统/DSH 升级后桥接起不来 | 旧 venv 指向的 DSH 自带 Python 已不存在 | 换独立 venv，`setup.cmd` 可重建 |
| 9 | 在慢速 U 盘上建 venv 卡死（`pip -V` 近 4 分钟） | U 盘小文件写入极慢（约 0.15MB/s） | 运行环境放本地盘，U 盘只放数据 |
| 10 | 自启 VBS 报「未结束的字符串常量」 | cscript 按 ANSI 解析 UTF-8 中文注释 | VBS 全 ASCII + CRLF |
| 11 | 自启 VBS 用 `cmd /c` 拼接命令失败 | cmd 引号规则 | 直接用 `sh.Run pythonw ...` |
| 12 | `.cmd` 非交互调用冒两行报错 | LF 换行的批处理 | `.gitattributes` 固定 CRLF |
| 13 | `.ps1` 中文乱码/生成乱码目录 | 无 BOM 的 UTF-8 被 PowerShell 5.1 当 ANSI | `.ps1` 存 UTF-8 with BOM |

**设计沉淀**：Windows 脚本编码三件套（`.cmd` CRLF、`.ps1` UTF-8 BOM、`.vbs` ASCII）
已写入 `CONTRIBUTING.md`，并由 `.gitattributes`/CI 守护。

## 经验总结（给后来者）

1. **先跑通最小闭环，再堆功能**：认证 → 收消息 → 回消息 → 真执行 → 文件回传，每一步单独验证。
2. **平台限制要写进产品设计**：10 分钟流式上限、单长连接、主动推送权限，都是硬约束。
3. **错误要分级**：「没接上」可以换路，「接了但失败」不能重试——否则会造成重复执行。
4. **无人值守 = 全权限**：自动审批是便利，也是风险，必须默认披露、可关闭。
5. **Windows 脚本编码是真实成本**：中文注释、BOM、CRLF、ASCII 约束，不处理好会反复翻车。
6. **日志要能脱敏**：密钥掩码、聊天内容截断、分享前提示，保护用户隐私。
7. **慢速介质不要放运行环境**：U 盘/网络盘只放程序与数据，环境放本地盘。
8. **把开发日志留好**：既是排障资料，也是（如需要）软件著作权登记的证明材料。
